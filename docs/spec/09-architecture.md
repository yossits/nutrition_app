## 2. ניהול מפתחות API

**אף פעם לא לשמור מפתח API בתוך קובץ בריפו.** בוטים סורקים את זרם האירועים הציבורי של GitHub ומוצאים מפתחות תוך דקות.

המפתח נמסר כמשתנה סביבה בלבד:

```bash
# בחר את השורה של ה-shell שלך:

# Windows — cmd
set ANTHROPIC_API_KEY=sk-ant-...

# Windows — PowerShell
$env:ANTHROPIC_API_KEY = "sk-ant-..."

# Mac / Linux
export ANTHROPIC_API_KEY=sk-ant-...
```

ב-PowerShell, `set` הוא alias ל-`Set-Variable` ואינו מגדיר משתנה סביבה — הוא יוצר משתנה בשם `ANTHROPIC_API_KEY=sk-ant-...` ולא מתריע. הסקריפט ייפול על "חסר מפתח" בלי שום רמז לסיבה.

ה-`.gitignore` חוסם `.env` וקבצי מפתחות. **אם מפתח נחשף אי פעם — לבטל אותו מיד ב-console.anthropic.com ולהנפיק חדש.** מחיקת הקומיט אינה מספיקה; הוא נשאר בהיסטוריה.

בייצור המפתח חי רק ב-Edge Function, לעולם לא בלקוח.

## 3. מודל הנתונים

```
users              — משתמשים ואימות
profiles           — נתונים אישיים, מין, גיל, גובה
health_screening   — תוצאות סינון, דגלים, תאריך
goals              — מטרה, משקל יעד, קצב
targets            — יעדי קלוריות ומאקרו מחושבים + היסטוריית שינויים
preferences        — אהוב/לא אוהב, אלרגיות, כשרות, מס' ארוחות
foods              — מאגר המזון, ערכים ל-100 ג'
food_servings      — יחידות הגשה לכל פריט
menus              — תפריט שנוצר, תאריך, סטטוס
meals              — ארוחות בתוך תפריט
meal_options       — אפשרויות בחירה בתוך ארוחה
meal_items         — פריטים בתוך אפשרות + כמות
weight_logs        — שקילות
adherence_logs     — סימוני "אכלתי"
subscriptions      — מנויים וסטטוס תשלום
profile_events     — יומן append-only של כל שינוי בפרופיל (שדה, ערך, מקור, valid_from)
free_text_inputs   — טקסט גולמי כפי שהוזן + השינויים שחולצו ממנו + אישור המשתמש
food_affinity      — ניקוד העדפה לכל פריט מזון: score, signal_count, source, updated_at
menu_archive       — כל תפריט שנוצר אי פעם + snapshot של הפרופיל שממנו נבנה
refresh_log        — ריענונים חודשיים: מה נתבקש, מה השתנה, מתי
```

הסכימה המפורטת של `foods` ו-`food_servings` נמצאת ב-`../../db/01_food_db_schema.sql`.

**עקרון:** טבלאות ההעדפות והפרופיל אף פעם לא נמחקות ולא נדרסות. עדכון שווה שורה חדשה. זה מה שמאפשר ללמוד לאורך זמן ולהסביר החלטות בדיעבד.

**כל טבלה עם מידע אישי — RLS מופעל, משתמש רואה רק את השורות שלו.** טבלאות המזון הן נתוני ייחוס ציבוריים ואינן דורשות RLS.

## 4. גבול AI / קוד

**הכלל: AI רק היכן שאין תשובה נכונה אחת. כל דבר שיש לו תשובה נכונה — קוד.**

זה לא בעיקר שיקול עלות. זה שיקול של דטרמיניזם, אפשרות אימות, ובטיחות.

### 4.1 מפת הפעולות

| פעולה | קוד | AI |
|---|---|---|
| BMR / TDEE / חלוקת מאקרו | ✓ | |
| רצפות בטיחות | ✓ | |
| טריגר מעבר שלב + חישוב מחדש | ✓ | |
| גזירת זמני ארוחות מקימה/שינה | ✓ | |
| **סינון המאגר לפי הפרופיל** | ✓ | |
| ולידציה של תפריט מול היעדים | ✓ | |
| ספירת מכסת בקשות | ✓ | |
| החלפת מזון בודד בשקול | ✓ | |
| פריסה מחדש — חלוקת היעדים | ✓ | |
| רשימת קניות, גרפים, ממוצע נע | ✓ | |
| **הרכבת ארוחה** | | ✓ |
| **חילוץ שדות מטקסט חופשי** | | ✓ |
| **סיווג בטיחות של טקסט חופשי** | | ✓ |

**שלוש פעולות בלבד דורשות AI.** כל השאר הוא קוד.

### 4.2 החיסכון הגדול: לסנן לפני שמבקשים

הטעות היקרה היא לשלוח את המאגר למודל ולבקש ממנו להתחשב באילוצים.

```
❌  4,500 פריטים → מודל → "אל תשתמש באגוזים, שמור על כשרות"
✓   4,500 → אצירה → 350 → סינון לפי פרופיל → ~200 → דגימה → 70 → מודל
```

**שלושה שלבים, לא אחד:**

| שלב | מ־ | אל | איך |
|---|---|---|---|
| אצירה | 4,500 | 300–400 | דגל `menu_eligible`, חד-פעמי |
| סינון | 350 | ~200 | SQL: כשרות · אלרגנים · לא-אוהב · בישול · מחיר |
| **דגימה** | 200 | 60–80 | מכסה לכל קטגוריה, משוקללת בניקוד ההעדפה |

**שלב הדגימה הכרחי.** סינון לבדו מוריד רק כ-40%, נמדד על 94 פרופילים. בלעדיו הפרומפט נשאר גדול פי כמה מהנדרש.

**וזו לא רק חסכון — זו הגנת הבטיחות החזקה ביותר במוצר.** אלרגן שלא נכנס לפרומפט לא יכול להופיע בפלט.

### 4.3 מנופים נוספים

| מנוף | הסבר |
|---|---|
| **Prompt caching** | הסכמה, הכללים וההוראות זהים בכל ייצור. לשמור במטמון; רק הפרופיל משתנה |
| **שלד לשימוש חוזר** | פרופילים דומים חולקים מבנה תפריט מאומת; ההחלפות נעשות בקוד |
| **החלפה = שאילתה** | "החלף את חזה העוף" הוא `SELECT` לפי קטגוריה וטווח מאקרו. לא צריך מודל |
| **סכמת פלט קשיחה** | JSON מובנה מקצר פלט ומייתר פרסינג |

מתוך ארבעת סוגי בקשות השינוי, **שניים לא דורשים AI כלל.**

### 4.4 המלכודת בכיוון ההפוך

אל תנסה לכתוב את שלב **הרכבת הארוחה** בקוד. פותר אילוצים שבוחר פריטים כדי לפגוע ביעד מאקרו מייצר ארוחות נכונות מתמטית שאף אדם לא יאכל — 300 גרם ברוקולי ו-4 כפות שמן כדי לסגור את יעד השומן.

זו בדיוק המשימה שבגללה יש AI בלולאה. לחסוך שם זה לחסוך במוצר עצמו.

### 4.5 מה באמת המגבלה

עלות הטוקנים בארכיטקטורה הזו היא סנטים בודדים למשתמש לחודש, ולא הגורם המגביל. **המגבלות האמיתיות הן זמן תגובה ואמינות.** כל קריאת AI היא נקודה שבה האפליקציה יכולה להיות איטית, לא-דטרמיניסטית, או להיכשל בוולידציה. צמצום שטח ה-AI הוא בראש ובראשונה שיקול הנדסי, ורק אחר כך תקציבי.

## 5. מפת הקוד — `spike/`

| קובץ | תפקיד | להריץ? |
|---|---|---|
| `foods.py` | 63 פריטי מזון, יחידות עבריות, כשרות, אלרגנים, דירוג איכות | לא |
| `engine.py` | BMR · TDEE · מאקרו · רצפות בטיחות · זמני ארוחות | לא |
| `filters.py` | סינון לפי פרופיל · מספיקות מאגר · דגימה · ולידטור | לא |
| `portions.py` | פותר-המנות + ניסוח עברי של כמויות | לא |
| `generator.py` | קריאת API, פרומפט, לולאת ניסיון חוזר | לא |
| `profiles.py` | 100 פרופילי בדיקה, כולל 5 עוינים | לא |
| **`run_spike.py`** | בדיקת הליבה הדטרמיניסטית | **כן** — בלי מפתח |
| **`run_generation.py`** | מדידת שיעור המעבר מול ה-API | **כן** — עם מפתח |
| **`show_menus.py`** | מייצר `menus.html` לבדיקה ויזואלית | **כן** — עם מפתח |
| `spike_output.txt` | פלט אחרון של `run_spike.py` | — |

**להריץ:**

```bash
pip install -r requirements.txt
cd spike

python run_spike.py                 # ליבה דטרמיניסטית, ללא מפתח

set ANTHROPIC_API_KEY=sk-ant-...              # cmd
$env:ANTHROPIC_API_KEY = "sk-ant-..."         # PowerShell
python run_generation.py 40         # שיעור מעבר מול ה-API
python show_menus.py 8              # יוצר menus.html לפתיחה בדפדפן
```
